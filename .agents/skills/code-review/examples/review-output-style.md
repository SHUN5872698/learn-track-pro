# コードレビュー 出力フォーマット・トーン見本

このファイルは `SKILL.md` のStep 4で参照するレビュー結果の出力フォーマットとトーンの見本を定義する。

---

## 出力フォーマット

### 基本構造

```
## レビュー結果サマリー

- 🔴 Critical: X 件
- 🟡 Warning: Y 件
- 🟢 Suggestion: Z 件

---

## 指摘一覧

### [🔴 Critical] ファイル名:行番号

**問題**: ...（何が問題か、なぜ問題なのかを簡潔に説明）

**改善案**:
\`\`\`php（または js）
// 改善後のコード例
\`\`\`

---

### [🟡 Warning] ファイル名:行番号

**問題**: ...

**改善案**: ...（コード例、または文章で改善方法を説明）

---

### [🟢 Suggestion] ファイル名

**提案**: ...（任意対応であることが伝わる表現で記載）

---

## 総評

（全体的な印象、良かった点、改善の方向性を建設的なトーンで記載）
```

---

## フォーマットの各要素の説明

| 要素 | 説明 |
|------|------|
| `## レビュー結果サマリー` | 指摘件数を分類別に一覧表示する。レビュー全体のボリューム感を伝える |
| `### [🔴 Critical] ファイル名:行番号` | 行番号が特定できる場合は `ファイル名:行番号`、できない場合は `ファイル名` のみ記載 |
| `**問題**:` | 何が問題か、なぜ問題なのかを1〜3文で簡潔に説明する |
| `**改善案**:` | コード例が効果的な場合はコードブロックを使用する。文章のみでも可 |
| `## 総評` | 最後に必ず記載する。良かった点を必ず1つ以上含める |

---

## トーンガイドライン

### 基本方針：建設的・励ます

- **良い点を必ず認める**: 指摘だけで終わらず、コードの良い部分に1点以上言及する。ただし個人開発のため過度な励ましや感嘆表現（「頑張りましょう！」等）は避け、簡潔に留める
- **断定的すぎない表現を使う**: 「〜してください」より「〜することを検討してみてください」
- **理由を説明する**: なぜその指摘が重要なのかを添える
- **Suggestionは任意であることを明示する**: 「〜すると、より読みやすくなります」など

### 表現例

| 分類 | 推奨表現 | 避ける表現 |
|------|--------|----------|
| 🔴 Critical | 「〜のリスクがあるため、修正が必要です」 | 「ダメです」「バグです」 |
| 🟡 Warning | 「規約では〜とされているため、対応を推奨します」 | 「間違っています」 |
| 🟢 Suggestion | 「〜するとコードがより読みやすくなります」 | 「絶対に〜すべきです」 |

## 指摘一覧

### [🔴 Critical] app/Http/Controllers/UsersController.php:45

**問題**: 生のSQLクエリにユーザー入力値を直接埋め込んでいます。SQLインジェクションのリスクがあり、データベース全体が攻撃される可能性があります。

**改善案**:
```php
// 修正前（危険）
DB::select("SELECT * FROM users WHERE name = '{$request->name}'");

// 修正後（安全）
DB::select('SELECT * FROM users WHERE name = ?', [$request->name]);
// または Eloquentを使用
User::where('name', $request->name)->get();
```

---

### [🟡 Warning] app/Http/Controllers/UsersController.php:10

**問題**: `declare(strict_types=1);` が宣言されていません。プロジェクトのコーディング規約（`laravel-coding-standards.md`）では全PHPファイルへの宣言が必須とされています。

**改善案**: ファイル先頭に `declare(strict_types=1);` を追加してください。

---

### [🟡 Warning] app/Http/Controllers/UsersController.php:30

**問題**: Controllerに直接ビジネスロジックが記述されています。規約ではControllerはHTTPリクエスト/レスポンスの処理のみを担当し、ビジネスロジックはServiceクラスに委譲する設計としています。

**改善案**: 該当ロジックを `app/Services/Application/UserService.php` に移動し、Controllerからはサービスを呼び出す形に変更することを検討してみてください。現状Service層は段階的に導入中のため、優先度に応じて対応いただければ問題ありません。

---

### [🟢 Suggestion] app/Http/Controllers/UsersController.php

**提案**: `index` メソッドの変数名 `$d` を `$users` のような説明的な名前に変更すると、コードの可読性が上がります。任意の対応ですが、将来のメンテナンスが楽になります。

## 総評

全体的にコードの構造は整理されており、FormRequestを使ったバリデーション実装は適切でした。SQLインジェクションのリスクが1件あるため、そちらは優先して対応をお願いします。その他の指摘は段階的に対応いただければと思います。引き続き良いコードを一緒に作っていきましょう！
