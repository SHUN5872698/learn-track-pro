## SKILL.md

### 構成と判断理由

Issue #17の「Suggested Implementation」セクションに示された構成（`name` / `description` / 使用方法 / レビュー手順 / 指摘分類と優先度 / 参照ファイル）をそのまま採用した。

ステップ形式（Step 1〜4）は仕様書の「レビュー手順（ステップ形式）」という指定に従い、**対象特定 → チェックリスト適用 → 分類 → 出力**という自然な作業フローに対応させた。

指摘分類の表はLaravelのレイヤー責任分離の扱い（🟡 Warning）をユーザー指示の補足に従いNote欄で明記した。

### 仕様書のどの方針が反映されたか

- `description` の文言はIssue #17の「Suggested Implementation」に記載された文面を使用
- 「レビュー手順（ステップ形式）」の指定に従い4ステップ構成を採用
- 「指摘の分類と優先度定義」として 🔴 Critical / 🟡 Warning / 🟢 Suggestion の3段階を定義
- `resources/review-checklist.md` と `examples/review-output-style.md` へのリンクを「参照ファイル」セクションに記載

### プロジェクト固有の調整点

- Laravelのレイヤー責任分離違反（ControllerにService層を通すべきロジック）を **🟡 Warning** として扱う旨を明示（ユーザー指示の補足に従う）
- 現状のService層導入状況（プロフィール画像アップロードのみ・段階的分離予定）をNote内に記載し、レビュアーが過度に Critical にならないよう配慮した

## resources/review-checklist.md

### 構成と判断理由

Laravel・Vue.js・共通（セキュリティ/パフォーマンス）の3セクション構成とした。SKILL.mdのStep 2が「Laravel/Vue.js/共通」を判定してから参照するフローになっているため、セクション分割が自然に機能する。

各チェック項目に `（🔴/🟡/🟢）` を末尾に付与することで、チェック中に即座に重大度を判断できるようにした。

### 仕様書のどの方針が反映されたか

- 「Laravel コーディング規約に基づくチェック項目」：`laravel-coding-standards.md` の全主要セクション（アーキテクチャ・コードスタイル・命名・Eloquent・API・エラーハンドリング）を網羅
- 「Vue.js コーディング規約に基づくチェック項目」：`vue-coding-standards.md` の全主要セクション（`<script setup>`順序・命名・状態管理・バリデーション・UI）を網羅
- 「共通チェック項目（セキュリティ、パフォーマンス等）」：セキュリティ・パフォーマンス・可読性を共通セクションとして定義

### プロジェクト固有の調整点

- `<script setup>` なし / Options API使用を **🔴 Critical** に設定した（仕様書にはCriticalの定義としてセキュリティリスク・バグ・動作不正とあるが、このプロジェクトではOptions API禁止が明示されているため最重要違反として扱う）
  - ただし、この点は「今後の改善余地」にも記載（仕様書の定義との厳密な整合性）
- Laravelのレイヤー責任分離違反を **🟡 Warning** として設定（SKILL.mdの定義と統一）
- Tailwindの禁止ブレークポイント（`sm:` / `xl:`）を明示的にチェック項目として追加（`vue-coding-standards.md` の明示的な規約に従う）

## examples/review-output-style.md

### 構成と判断理由

Issue #17の「Suggested Implementation」が示した出力フォーマット（`## レビュー結果サマリー` → `## 指摘一覧` → `### [🔴 Critical] ファイル名:行番号` → `**問題** / **改善案**`）をベースに、**フォーマット定義 → 要素説明 → トーンガイドライン → 実例** の構成とした。

実例を最後に配置したのは、フォーマットと要素の意味を先に理解してから実例を読む方が、AIが意図を正確に汲み取りやすいと判断したため。

### 仕様書のどの方針が反映されたか

- Issue #17の出力フォーマット例（サマリー件数・指摘見出し形式・問題/改善案の構造）をそのまま使用
- 「指摘の記載フォーマット（重大度 / 対象ファイル / 問題点 / 改善案）」を表形式で説明
- 「レビュー結果のサマリー形式」を冒頭の `## レビュー結果サマリー` セクションで実装
- 「トーンガイドライン（建設的・励ます）」を表（推奨表現 vs 避ける表現）で具体化

### プロジェクト固有の調整点

- Laravelのレイヤー責任分離指摘について、🟡 Warning の実例の文中に「現状段階的に導入中のため優先度に応じて対応いただければ」という表現を盛り込み、レビュアーが適切な温度感で伝えられるようにした
- `## 総評` セクションを必須として定義し、「良かった点を必ず1つ以上含める」ことをルール化（仕様書の「励ます」方針を具体化）

## 今後の改善余地・懸念事項

1. **Options API の分類（🔴 vs 🟡）**：`vue-coding-standards.md` では「Composition API使用、Options API禁止」と明記されているため 🔴 Critical として設定したが、Issueの仕様書における 🔴 Critical の定義（「セキュリティリスク・バグ・動作不正」）とは厳密には異なる。将来的に分類定義を拡張する際に見直しが必要かもしれない。

2. **テスト関連のチェック項目**：`laravel-coding-standards.md` にテスト規約（PHPUnit等）が記載されているが、「MVP段階では手動テストも許容」という注記があるため、今回はレビューチェックリストへの追加を保留した。テスト文化が成熟した段階でチェック項目として追加することを推奨する。

3. **Pinia のチェック項目が少ない**：技術スタックとしてPiniaが含まれているが、`vue-coding-standards.md` にPinia固有の規約の記述がほぼないため、チェック項目が限定的になっている。Piniaのストア設計規約が定義された段階で追記が必要。
